# Architecture

Kotlin Multiplatform: almost everything lives in `:shared` and runs on Android and iOS. Data
flows one way: the UI sends actions down and observes state coming back up.

```
shared/ (Kotlin Multiplatform: Android + iOS)
  commonMain/
    feature/      Compose Multiplatform screens + ViewModels (timer, statistics, history, settings)
       │  observes StateFlow, sends actions
    domain/       Pure Kotlin: models, TimerEngine, statistics, repository interfaces
       │  implemented by
    data/         Room KMP (timer_state, focus_sessions), DataStore (settings), repositories
    platform/     PlatformServices: what the UI needs from the OS (permissions, sharing, formats)
    app/          AppDependencies: the object graph the UI receives
    core/, navigation/
  iosMain/        iOS implementations: clock, storage, notifications, share sheet, photos,
                  MainViewController() shown by the Swift shell
app/ (Android)    Hilt graph, MainActivity, AlarmManager, notifications, receivers, FileProvider
iosApp/ (iOS)     SwiftUI shell generated by XcodeGen (project.yml), icon, Info.plist keys
```

### Android and iOS differences

| | Android | iOS |
|---|---|---|
| Session alert | Exact alarm wakes the app at the deadline; the transaction that records the session posts the alert | The app cannot be woken: every upcoming end (`TimerEngine.upcomingSessionEnds`) is scheduled up front as a local notification and re-planned on each change |
| Running timer outside the app | Ongoing notification with a large countdown | None yet (a Live Activity needs iOS 16.1 and a paid developer account) |
| Monotonic clock | `elapsedRealtime`, boot count | `CLOCK_MONOTONIC` (counts during sleep), boot time from `kern.boottime` |
| Alert sound | Picked in the app (channel sound) | Set in the Settings app |
| Dependency injection | Hilt | Built by hand in `IosAppDependencies` |

## Rules

* `domain/` imports no Android or framework classes, so the engine and the statistics run as plain
  JVM unit tests.
* Screens are stateless `XxxScreen(uiState, callbacks)` composables; a small route function wires
  the ViewModel. Previews and UI tests use the stateless version.
* ViewModels expose one `StateFlow<XxxUiState>`, built with `stateIn(WhileSubscribed(5_000))`.
* Time comes from the injectable `TimeSource`; nothing reads the system clock directly.
* Dependency injection with Hilt on Android; the shared code uses no DI framework. Android tests replace modules with `@TestInstallIn` (in-memory Room, fake
  clock, fake settings).

## The timer, end to end

1. The user taps Start → `TimerViewModel` → `TimerRepository.start()`.
2. The repository, in one Room transaction, settles the stored state, applies the action with
   `TimerEngine` and writes it back (see [TIMER_ENGINE.md](TIMER_ENGINE.md)).
3. `TimerSystemIntegration` (application scope) observes the new state and schedules the deadline
   alarm and the countdown notification.
4. The screen observes the same state and re-derives the remaining time once per second.
5. At the deadline, the alarm (or the open screen, whichever is first) calls `refresh()`; the
   session is recorded once and `SessionEndAlert` posts the alert.

## Storage

* Room: timer state and session history ([DATABASE.md](DATABASE.md)).
* DataStore Preferences: appearance and timer settings.
* Nothing leaves the device; the app has no network permission. Sharing a statistics card writes a
  JPEG to the app cache and hands it, through `FileProvider` and Android's share sheet, to the app
  the user picks; only that app gets read access to that one file. A photo for the card comes from
  the camera app (writing to a cache file it is granted for that capture) or Android's photo
  picker, so no camera or storage permission is requested; it is only kept in the cache.
